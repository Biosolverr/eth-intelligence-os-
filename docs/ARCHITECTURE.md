# Architecture (v5): three contracts, five layers, forward-only graded ledger, analyst bounty, bounded authority

## 1. Why GenLayer is structurally necessary — and where it is NOT
Consensus-dependent operations (layer readings for layers promoted to consensus, the overall verdict, and outcome resolution):
1. **Verdict** (`EthIntelligence.analyze`): interpretation of a bounded evidence snapshot. Validators independently re-run it; state changes only if they agree under the equivalence rule. *Level of necessity: interpretation consensus.* Input data are **submitter-asserted and unverified**, so this contract proves *"these validators agreed on what this asserted evidence implies"*, never *"the evidence is true"*.
2. **Outcome resolution** (`EthOutcomeLedger.resolve`): validators themselves fetch two historical hourly prices and must obtain identical values; the verdict is then scored hit/miss/abstain. Here validators ingest the evidence themselves (strongest use of GenLayer in this design). Without it, a verdict author could grade their own homework.
Remove GenLayer and you get a backend that can silently rewrite both the verdicts and their grading.

## 2. Contracts
| | `EthIntelligence` (verdict) | `EthOutcomeLedger` |
|---|---|---|
| Writes | `submit_snapshot`, `analyze_layer`, `analyze` (submitter only), `release_snapshot`, `republish`, `set_policy`, `set_ledger` | `register` (verdict contract only), `resolve`, `rebroadcast`, subscriber management (owner) |
| Consensus | custom leader/validator: re-execution; directional score (bullish +conviction, bearish -conviction, neutral 0) within 40, risk within 1 step, inconclusive only with inconclusive | custom: re-fetch; **exact** equality of both historical open prices (closed candles are immutable) |
| States | `SUBMITTED → RECORDED` (immutable) or `SUBMITTED → RELEASED` | `REGISTERED → RESOLVED` (immutable) |
| Link | after `RECORDED`, `emit(on='finalized').register(...)` | accepts only that sender; idempotent |
Deploy order: verdict (no args) → ledger(verdict_addr, price_url_template, flat_band_bps, max_price_deviation_bps) → `verdict.set_ledger(ledger_addr)` (re-pointable, see 2d) → bounty(ledger_addr) → `ledger.add_subscriber(bounty_addr)` (ledger owner).
Engine (`engine/`) is **not** ported on-chain (removal test: mechanism does not need it). It stays local, produces `risk` tagged `derived`, asserted by the submitter. Porting = separate phase (single-file contract, pure-Python, parity-tested).

## 2b. Layers: balance between arithmetic and AI judgement
Five layers keep the original idea (each layer reads its own data, then one overall assessment): **quant, flow, macro, manipulation, risk**.
Each layer has BOTH an arithmetic reading and an AI reading; a per-layer mode picks which one the verdict uses.
| Layer | Reads | Arithmetic reading (formula) | Default mode |
|---|---|---|---|
| quant | `price` | exact port of the engine "tech" block (rsi<60, atr<4) | arith |
| flow | `flows` | exact port of engine "flows" + "onchain" blocks, engine WDI weights .32/.20 | arith |
| macro | `macro` | engine "macro" block **(fear_greed, dxy only)**; hy_oas, yield curve, fed, breadth are seen only by the AI | **consensus** |
| manipulation | `price`, `derivs`, flags | exact port of engine suspicion index (caution 0–100) | **consensus** |
| risk | `risk`, `derivs`, `price` | NEW composition: threats_score + regime/liq/funding/ATR adjustments (the old risk agent was hard-coded rules) | arith |
* **Arith mode**: computed deterministically inside `analyze` (no transaction, no LLM). **Consensus mode**: its own transaction `analyze_layer(id, layer)` with its own leader/validator rule, result stored (immutable); a failed layer leaves everything else intact and only that layer is retried. `analyze(id)` refuses to run until every consensus-mode layer is stored, then does the overall consensus over all five readings.
* Layer rule: `inconclusive` flag equal, `|Δscore| ≤ 20`, `|Δcaution| ≤ 25`. Tolerance 20 < 2×band 15, so bullish-vs-bearish can never be equivalent (exhaustive test e02). Stance is *derived* from score (band ±15), never asked from the model: fewer exact-match fields, fewer Undetermined.
* Layer kinds: quant/flow/macro are **directional** (score −100..100); manipulation/risk are **caution** layers (no direction, stance "n/a"; they tell how far to trust the directional ones).
* The AI sees only its own layer's groups plus the arithmetic reading as a prior; it may deviate, and the deviation stays visible (`arith_prior` stored beside the AI reading).
* **Extensibility**: `set_layer_mode(layer, "consensus"|"arith")` (owner) promotes/demotes any layer with no code change; every layer already has its AI prompt and tests in both modes. Records store `layer_modes`, so old verdicts remain interpretable. Promoting all five = 5 layer rounds + final.
* Cost model (units, not dollars; official fee data not found): default = 3 consensus rounds per verdict (macro, manipulation, final) vs 1 before; all five promoted = 6. Rounds are separate transactions, so the failure of one does not discard the others.
* What was dropped: MSS/TSS (confusing semantics), corridor (needs levels not in the snapshot), Monte Carlo, humanity blend. Missing layer inputs ⇒ the layer is **inconclusive** (not treated as neutral), unlike the old engine which silently used defaults.

## 2c. Ledger grading rules (found in the hostile review; each has regression tests and mutants)
1. **Forward-only.** The graded window starts at the first full hour AFTER the verdict (`analyzed_at`), never at the submitter-asserted `observed_at`. Before the fix a snapshot claiming observation 23 h earlier had 96 % of a 1-day window already known (hindsight).
2. **No survivorship.** Counters track `registered`, `resolved`, `unresolved`, `excluded`; `get_unresolved_due_page` lists overdue entries so anyone can resolve them. A keeper resolving only flattering verdicts is visible (before: "1 hit of 1" while 3 were registered). Always compute rates over `registered`, never only over `resolved`.
3. **No pollution.** Scorecards are per submitter and global. Validators also fetch the observation-hour candle (open, high, low); if the asserted `price.current` lies outside that hour's [low, high] by more than `max_price_deviation_bps` (constructor, 50–2000, measured against the nearest bound) the verdict is **excluded** from hit/miss and counted as `excluded`. (It used to be compared with the hour OPEN only, which excluded honest intra-hour prices and pushed analysts to assert the open instead of the live price.)
4. **Three-candle strictness.** Leader and validators must obtain identical values: open, high and low of the observation candle and the opens of the start and end candles; every candle must be the requested hour, and an observation candle whose open lies outside its own high/low is refused.
5. **Subscribers keep their promise.** The ledger remembers who was subscribed when a snapshot was registered; removing a subscriber later does not strand the outcomes it was already promised (`rebroadcast` and `resolve` reach the registered set plus the currently active one).
6. **No clock inside a view.** `get_unresolved_due_page(offset, limit, now_s)` takes the time from the caller.
Still NOT solved (P3, to be decided with Studio data): one flat band (`flat_band_bps`) for every horizon, so short horizons make "neutral" hit too easily — show base rates (up/down/flat shares) next to hit rates and compare with a naive baseline; `conviction` is stored but never graded.

## 2d. Authority, limits, abuse (owner powers stated explicitly)
| Power / limit | Rule |
|---|---|
| Owner can | `set_policy(max_age 300 s–7 d, pause_hours 0–168, max_open_per_sender 1–1000)`; `set_layer_mode` (affects only FUTURE snapshots); `set_ledger` (≤5 changes, public `get_ledger_history`); `propose_owner` → new owner `accept_ownership` (two-step) |
| Ledger owner can | add/remove subscribers (bounded counts); a removed subscriber still receives the outcomes of snapshots registered while it was subscribed. Cannot change the price source, a recorded entry or a resolution |
| Owner cannot | alter any recorded verdict/layer result; block or retroactively tighten analysis of a submitted snapshot; change the layer modes of an existing snapshot (frozen at submit); pause longer than 168 h at a time; touch the ledger's price source (immutable at ledger deploy); grade anything |
| Pause | blocks only NEW `submit_snapshot`; analysis of already submitted snapshots always continues. Always self-expires. **Residual:** a hostile owner can re-pause intake repeatedly (censorship of new work); mitigation = move ownership to a multisig contract (not built) |
| Freshness rule | `max_age` is frozen per snapshot at submit; tightening the policy is not retroactive |
| Who analyzes | only the snapshot's submitter (`analyze`, `analyze_layer`); a stranger can neither choose when someone else's snapshot is recorded nor make a bounty ignore it |
| Open snapshots | ≤ `max_open_per_sender` (default 20) submitted-but-unrecorded per sender; a recorded verdict or `release_snapshot` frees a slot (the submitter any time; anyone once the snapshot is stale). **Residual:** Sybil accounts bypass it; storage growth is bounded only by fees (fee model UNKNOWN) |
| `republish` | ≤3 per snapshot (each emission is a child tx on the ledger) |
| Frozen modes | layer modes are stored per snapshot at submit; the owner can no longer swap an AI reading for a formula after seeing it (was possible; test m04 now asserts the opposite) |
| Conviction bound | final conviction ≤ min(structure cap, layer cap); layer cap = 100 − max(caution of non-inconclusive caution layers)//2 (floor 10). Before, caution layers had no deterministic effect (caution 100 allowed conviction 95). Direction is never changed by caps |
| UI/client | the server signer signs for every visitor ⇒ protocol actions are locked unless `ETH_UI_PASSWORD` is entered or `ETH_UI_LOCAL_ONLY=1`; contract address pinned by `ETH_INTEL_CONTRACT` (others need explicit confirmation); finality shown = WEAKEST of all transactions in the run (layers + final), earlier-run layers count as UNKNOWN; the dry-run view is advisory (a rejection `[EXPECTED]` stops, a view that merely fails does not block the tx path) |

## 2e. `EthAnalystBounty` (stake on a verdict; no owner, no pause, no upgrade)
A client escrows a reward for a verdict at a given horizon; one analyst commits with an equal bond; the analyst's verdict reaches the bounty from the ledger (`on_verdict`), and the ledger's resolution settles the money (`on_resolution`). Both are accepted only from the ledger address fixed at deploy.
| Step | Rule |
|---|---|
| `create_bounty(horizon_days 7-90, commit_window_s, delivery_window_s 1 h-48 h, min_conviction)` | payable; the reward is locked and the bounty id is returned; `cancel_bounty` only while OPEN. Invalid arguments do NOT revert: the attached value is credited back to the sender (`withdraw`), the reason is stored (`get_rejection(account)`: `reward_too_small`, `horizon_days_out_of_bounds`, `commit_window_s_out_of_bounds`, `delivery_window_s_out_of_bounds`, `min_conviction_out_of_bounds`) and an empty string is returned |
| `commit(id)` | payable, `value == reward`, first come first served, before the commit deadline; the client can no longer cancel. Returns true on success. Any refusal (`unknown_bounty`, `bounty_not_open`, `commit_window_closed`, `client_cannot_commit`, `bond_must_equal_reward`) credits the value back and returns false |
| delivery | the verdict's submitter must be the analyst, the horizon must match, conviction >= min, `analyzed_at` between the commit time and the delivery deadline. Anything else is **not** applied and the reason is stored (`get_ignored(snapshot_id)`: `horizon_mismatch`, `conviction_below_min`, `outside_delivery_window`, `bounty_not_committed`); only the committed analyst's own snapshots can write such a record |
| settlement | `hit` with bullish/bearish: analyst gets reward + bond. `miss` or `excluded`: client gets reward + bond. `abstain`, `neutral` hit, `inconclusive`: each side gets its own money back. An **inconclusive** delivery settles immediately (no waiting for the horizon) |
| no delivery | after delivery deadline + 3 days anyone calls `expire`: the client gets the reward back and the analyst's bond is **forfeited** (`forfeited_total`, stays in the contract). Reason: whoever can make a delivery fail (verdict-contract owner pausing intake, a re-pointed ledger, a removed subscriber) must not profit from it |
| no resolution | after the resolve deadline (horizon + 14 days) `expire` refunds both sides |
| money | pull payments only (`withdraw`); `get_solvency` checks `balance >= claimable + locked + forfeited` and reports `unaccounted` (balance above everything owed) |
Why refunds instead of reverts: on the hosted Studio a refused payable call kept the attached value (observed live, U20: 25 to 24 GEN for the sender, 153 to 154 GEN for the contract, 94 GEN stuck in total), and the contract has no owner who could return it. A plain value transfer without a method is not supported (the linter rejects a `__receive__` method); such funds would show up as `unaccounted`. Known limits: a bounty is a single-outcome bet (cannot distinguish skill from luck; it is not a skill score); `neutral` can at best return the bond and is dominated by `inconclusive`; the analyst chooses the stance, and the evidence behind it is self-asserted; the bounty trusts the ledger it was deployed against. Analysts should submit their snapshot BEFORE committing (a snapshot analyzed before the commit is ignored); pause only blocks new intake, so an already submitted snapshot can still be analyzed.

## 3. Evidence model (honest version)
Snapshot (`schema_version "1"`): `price` (required: current, ret_7d, atr_pct), ≥2 of `derivs|flows|macro|risk`, allow-listed `flags`, ≤12 `sources{group, source_id, observed_at, kind∈raw|derived}`; ≤6000 B; unknown keys rejected; no free text anywhere; NaN/Inf/bool rejected; explicit-timezone timestamps. **Social layer removed.**
**Everything — values, timestamps, source ids and `kind` — is asserted by the submitter.** `kind` carries no scoring weight (found in review: it used to raise the conviction cap 75→100 when merely claimed; fixed, regression test t62). Records carry `evidence_trust: "submitter_asserted"`. The conviction cap uses only structure the contract can see (missing / stale-as-asserted / unsourced groups).

## 4. State, finality, appeals (from the official Finality & Appeals pages)
* A reverted/undetermined tx leaves no storage change; "pending/undetermined/failed" are protocol tx statuses, never invented contract states.
* **Accepted is provisional.** An appeal (anyone, by bond; fresh larger committee) can overturn it and force recomputation of later non-finalized txs of the same contract. Clients therefore label every record **FINAL / PROVISIONAL / UNKNOWN** from `get_transaction().status_name` (`classify_tx_status`). Without a tx hash finality is UNKNOWN, never assumed final.
* **Undetermined is appealable**: a leader appeal may still yield a result → UI says so instead of "failed".
* The ledger receives verdicts via `emit(on='finalized')`: it never sees one that could still be overturned. Recovery if the child tx fails: `republish(id)` (idempotent).
* Shared-fate caveat (residual F-D): all analyses live in one contract, so an appeal on an early tx can force recomputation of later ones. Isolation (factory per snapshot) is out of scope.

**Verdict equivalence rule (changed after live data).** The first rule (stance exact, conviction within 20, risk within 1 step) failed too often on the live validator set: of 9 live `analyze` runs only 4 were accepted in the first round, 3 needed one or two leader rotations and 2 ended `UNDETERMINED` after three rotations (both with 30-day snapshots; the 7-day ones fared better, but the sample is tiny). The rule now compares a directional score (bullish = +conviction, bearish = -conviction, neutral = 0): results are equivalent when the scores differ by at most 40 and `risk_level` by at most one step; two results with the same stance compare their convictions with the same tolerance of 40; `inconclusive` only matches `inconclusive`. So a weak bullish (up to 40) and a neutral are equivalent, a strong bullish and a neutral are not, and bullish never matches bearish unless both are weak. The recorded verdict is still exactly the leader's output. Consequence for readers: a verdict may be up to 40 conviction points away from what another validator would have produced, and a weakly directional verdict is not distinguishable from neutral by consensus. The effect on the undetermined rate has to be measured on a fresh deployment; no rate is claimed.
